# XiaoH 评审系统历史（已移除）

本文是 XiaoH 3.1.2 唯一保留的评审逻辑历史说明，仅供理解旧版本和迁移判断，不是当前运行规范。

## 演进

- 2.3.0：加入 Spec+RFC 准入和 Spec/OpenSpec 一致性审核。
- 2.15.0：所有实现任务开始要求多角色本地代码评审。
- 2.17.3：非评审产品能力稳定，版本包含 20 个 Skill 和 8 个 Agent。
- 3.0.0：评审演化为有界 Campaign，包含准备、首轮发现、批量修复、修复就绪、收敛复核和收口，并引入评审对象、语义补丁集、证据包、发现账本、角色证明和历史继承。
- 3.1.0：用户决定移除代码评审状态机与自动复查机制，不兼容旧协议。
- 3.1.1：恢复两个按需、单次的需求工件检查 Skill，但不恢复 Campaign、代码评审 Agent 或代码交付门禁。
- 3.1.2：修复工作台兼容定制被 Doctor 误报为降级的问题，不改变评审能力边界。

## 为什么移除

旧流程把“检查代码”变成第二套交付状态机。局部轮次虽然有上限，但修复不完整、评审对象变化、证据漂移和评审内核变化会重开 Campaign，导致整体时间不可预测。评审发现与修复交错，也容易只修一个表现而漏掉同根因路径。更关键的是，评审内核自身需要新的证明和复核，治理成本逐步超过实际收益。

## 当前替代方式

3.1.2 使用已确认需求基线、明确写入范围、根因修复、风险相称的测试/构建/静态/契约/安全校验，以及可追溯运行记录。失败会回到实现并重跑受影响的确定性检查，不会自动产生评审轮次。两个需求工件检查 Skill 可按需给出当前修订的一次性结论；普通代码审阅仍不属于 XiaoH 的产品门禁、Agent 目录或生命周期状态。

## 历史名词

旧资料中可能出现 Review Campaign、Review Unit、Semantic Patch Set、Evidence Envelope、Finding Ledger、Repair-Ready、R1/R2/P3 等名词。3.1.2 运行时、Skill、Agent、Hook、validator 和安装清单均不再识别这些协议。
