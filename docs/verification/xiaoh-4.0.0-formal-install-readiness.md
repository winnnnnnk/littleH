## 三、生成并确认真实本机安装计划

- [ ] 只读 Plan 正确识别真实 Codex Home、XiaoH 配置、Vault 和插件来源。
- [ ] Plan 完整列出预计写入、预计删除、保留资产、冲突、未解决项和恢复条件。
- [ ] 确认 Vault 路径和 `.obsidian` 标记正确，用户笔记与定制模板不会被覆盖。
- [ ] 确认自定义 Agent、Workspace 注册、自动化偏好和非敏感集成引用按规则保留。
- [ ] 确认磁盘空间、目录权限、路径占用和受管符号链接检查通过。
- [ ] 创建并校验恢复清单。每个备份项都必须有来源、备份路径、恢复目标、摘要和大小。
- [ ] 用户审阅 Plan 后，明确批准 4.0.0、来源 commit、目标路径和实际写入范围。

Plan 未通过或授权范围不精确时，不得开始第一次本机写入。

## 四、执行正式安装事务

当前 Doctor 报告为 `installation_status=not_installed`，因此正式部署应走干净 Setup，而不是把旧内部运行时当作兼容升级来源。

- [ ] 使用已确认的 4.0.0 候选和真实 Plan 启动一次受管安装事务。
- [ ] 在第一次写入前完成候选校验、恢复清单和备份摘要校验。
- [ ] 事务记录每个阶段和全部实际写入，不得只记录预计变更。
- [ ] 安装后的静态 Doctor 不得出现 managed-runtime、Agent、Hook 或 Validator 缺失。
- [ ] 安装回执准确返回 `restart_required`、`trust_required` 或 `runtime_unverified`，不得提前声明 `verified`。
- [ ] 安装过程不得修改 Playbook CLI 版本、插件缓存所有权或代替用户信任 Hook。

第一次写入后的任何失败都必须触发补偿恢复。恢复摘要不完整时状态只能是 `recovery_required`。

## 五、完成重启、信任和运行时验收

- [ ] 用户退出并重启 Codex，使新插件、Skill 和 Hook 进入新进程。
- [ ] 用户审阅并信任 `block_reserved_root_agent.py`、`guard_task_writes.py` 和相关受管 Hook。
- [ ] 从新根任务运行 `doctor --runtime`，而不是沿用安装前任务的加载状态。
- [ ] Doctor 确认插件版本、已加载 Skill、受管文件摘要、五个专业 Agent、Hook 注册和信任、Validator、Vault 及配置一致。
- [ ] 执行一次隔离的根任务冒烟验收，覆盖根执行绑定、受控验证证据和范围证明。
- [ ] 执行一次真实的专业 Agent 委派验收，确认 `SubagentStart` 上下文、一次性绑定、回执、转录和停止证明完整。
- [ ] 必需自动化 `xiaoh.daily-progress` 完成绑定并读回；若暂不启用，必须明确记录为降级能力。

只有运行时 Doctor 和两项隔离冒烟验收都通过，4.0.0 才能标记为本机正式激活。

## 六、安装后观察和回滚边界

- [ ] 在运行时验收完成前保留恢复清单、备份和事务回执。
- [ ] 在至少一个稳定工作周期内保留可恢复备份；清理时间由用户另行确认。
- [ ] 记录 Workspace 缺少 Darwin 根和自动化缺失等非核心降级项，不把它们伪装成核心运行时失败。
- [ ] 发现 Hook 未信任、上下文漂移、范围证明失败、用户资产异常或受管摘要漂移时，停止副作用并恢复到已知状态。
- [ ] 恢复完成后重新运行静态 Doctor；需要重新激活时，再由用户重启、信任并执行运行时 Doctor。

## 正式完成标准

以下条件必须同时成立：

1. 代码来源由唯一 commit SHA 和候选摘要固定。
2. 本地与远端阻断门禁全部通过。
3. 用户确认真实安装 Plan 和恢复条件。
4. 安装事务提交且没有未恢复写入。
5. 用户完成重启和 Hook 信任。
6. 新根任务的运行时 Doctor、根执行冒烟和真实委派冒烟全部通过。
7. 最终状态记录为 `installation_status=files_installed` 且 `activation_state=verified`。

在此之前，只能称为代码候选、已部署或运行时未验证，不能称为正式安装完成。
