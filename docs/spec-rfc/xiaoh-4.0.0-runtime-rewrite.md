# XiaoH 4.0.0 全面运行时重构 Spec+RFC

- 修订：4
- 状态：已确认
- 意图域：`global_agent_capability`
- 确认基线：保留 XiaoH 3.1.2 产品能力和用户长期资产导入语义；不兼容旧内部运行时、安装状态、事务证据和内部 Schema；代码完成后停在可安装候选状态，不安装本机。

## 1. 背景与目标

### 1.1 背景

XiaoH 3.1.2 已完成根任务身份收敛、5 个专业 Agent、旧代码评审 Campaign 删除、两个需求工件评审 Skill、2.x 运行时断代、初步运行时模块化、插件来源与内容漂移验证，以及 Workspace、Vault、自动化和 Playbook 边界。

当前实现仍存在结构性问题：模块之间大量使用星号导入，依赖方向不清晰；`plugin_state.py` 同时承担插件事实、第三方 Skill、配套能力和 Playbook 检查；Doctor 仍是大型函数，并会在已有错误或首个命令错误后停止部分诊断；安装器在备份后直接删除和覆盖真实目标，没有隔离候选、完整事务日志和补偿恢复；安装计划与 `actual_writes` 不能完整表达预计和实际变更；第三方 Skill 治理大量硬编码；故障注入、恢复、幂等和跨平台异常测试不足。

因此 XiaoH 4.0.0 采用全面重写，不再在 3.1.2 内部结构上继续叠加修补。

### 1.2 业务目标

- 建立职责清晰、依赖单向、可独立测试的运行时架构。
- 保留 3.1.2 已确认的产品能力和安全边界。
- 将安装重构为可计划、可验证、可恢复的补偿事务。
- 让 Doctor 一次返回全部可安全执行的诊断结果。
- 明确区分代码候选、文件部署、重启、Hook 信任和运行时验收状态。
- 建立 Manifest 驱动的第三方 Skill 治理。
- 将代码评审恢复为显式、单次、非门禁能力，不恢复旧评审 Campaign。
- 将编码执行划分为快速、标准和高风险三档，按影响面验证并一次性收敛失败，避免所有任务套用同一重流程。
- 在仓库和临时环境中完成开发与验证，不安装本机。
- 新实现验收后删除旧生产实现，不长期维护两套代码。

### 1.3 用户/利益相关者目标

- 用户一次看到完整问题集，不再反复执行“发现一个、修一个、再发现一个”。
- 用户在未来安装前能够看到预计写入、冲突、备份和恢复条件。
- 用户能够区分“代码完成”“文件已部署”和“当前进程已激活”。
- 用户长期资产不会因干净安装丢失。
- 维护者可以在单一模块内修改诊断、安装、Workspace、Vault 或 Skill 治理规则。
- 测试可以在临时目录完整模拟安装和故障，不依赖真实本机状态。
- 插件管理器、Playbook CLI 和 Hook 信任的人工边界保持清晰。
- 小型局部修复可以直接完成，高风险变更仍保留完整需求、安全和恢复门禁。

## 3. 功能需求

### FR-001：保留 3.1.2 产品能力基线

- **描述**：当 4.0.0 重写完成时，系统必须保留已确认的 3.1.2 产品能力，不得因内部重写静默删除功能。
- **验收标准**：
  - 保留根身份、5 个专业 Agent、正式委派、需求路由、Workspace、Vault、知识管理、自动化和 Playbook 只读集成。
  - 保留当前 27 个能力对应的产品结果；允许合并重复 Skill，但不得丢失行为。
  - 每项保留能力均有契约测试或可执行验证。
- **优先级**：必须
- **类型映射**：业务、用户、功能
- **来源**：用户确认；3.1.2 当前实现

### FR-002：保持根身份与委派安全模型

- **描述**：当 XiaoH 协调任务或委派专业 Agent 时，系统必须保持当前根身份和正式委派安全模型。
- **验收标准**：
  - `xiaoh` 不注册为子 Agent。
  - 只保留 `frontend_implementer`、`java_architect`、`java_code_explorer`、`java_implementer` 和 `pki_domain_expert`。
  - 正式委派继续要求有效任务上下文、authority hash、一次性 execution binding、角色匹配和完整回执。
  - Hook 缺失、未信任、绑定过期、上下文漂移或证明不完整时失败关闭。
- **优先级**：必须
- **类型映射**：业务、功能、安全
- **来源**：用户确认；全局执行契约

### FR-003：建立单向模块架构

- **描述**：当运行时代码调用领域规则或外部系统时，系统必须通过明确分层和接口完成，不得依赖星号导入或循环模块关系。
- **验收标准**：
  - 代码按 domain、application、ports、adapters、installation、diagnostics、capabilities、config、workspace、automation、vault 和 interface 划分。
  - `domain` 不依赖文件系统、环境变量、subprocess 或 Codex API。
  - 所有模块使用显式导入。
  - 自动依赖检查确认不存在禁止方向和模块循环。
- **优先级**：必须
- **类型映射**：解决方案、功能
- **来源**：用户确认；代码分析

### FR-004：重写配置、Workspace、Vault 和自动化模块

- **描述**：当系统读取、修改或验证配置、Workspace、Vault 和自动化时，各领域必须由独立模块维护其规则和生命周期。
- **验收标准**：
  - 配置锁、读取、合并、Schema 校验和原子写入只有一个实现位置。
  - Workspace 注册、跨平台绑定、冲突检测和路径解析只有一个实现位置。
  - Vault 明确区分用户内容、受管模板和历史内容。
  - 自动化模板、稳定身份、用户偏好、绑定、读回和重复检测由 automation 模块维护。
  - Doctor 和安装器只调用公开接口，不复制内部规则。
- **优先级**：必须
- **类型映射**：功能、解决方案
- **来源**：用户确认；当前模块分析

### FR-005：生成完整安装计划

- **描述**：当用户或测试请求安装计划时，系统必须在不写入目标环境的前提下返回完整计划。
- **验收标准**：
  - 计划包含目标版本、路径、资产分类、冲突、预计创建、预计覆盖、预计删除、预计保留和依赖条件。
  - 计划包含候选来源、备份需求、恢复条件和激活后续操作。
  - `actual_writes` 在计划阶段为空，但 `expected_writes` 必须完整。
  - 计划生成不得修改配置、插件、Vault、自动化或受管目录。
- **优先级**：必须
- **类型映射**：用户、功能
- **来源**：用户确认；3.0.0 参考设计

### FR-006：隔离构建运行时候选

- **描述**：当安装或更新准备部署新运行时时，系统必须先在隔离目录生成完整候选并验证。
- **验收标准**：
  - 候选包含 Agent、Hook、Validator、公共契约、配置模板、Vault 受管模板和运行时文件。
  - 候选通过文件清单、摘要、Schema、路径、权限和占位符检查。
  - 路径占位符替换后必须重新计算运行记录模板引用的任务上下文摘要。
  - 候选来源无法独立验证时返回 `unverified` 或 `failed`。
  - 候选失败时不得备份、删除或修改目标运行时。
- **优先级**：必须
- **类型映射**：解决方案、功能
- **来源**：用户确认；参考设计

### FR-007：建立恢复清单和完整备份

- **描述**：当事务准备执行第一次受管写入时，系统必须先完成可验证备份并形成恢复清单。
- **验收标准**：
  - 每个备份项记录类型、来源、摘要、备份位置和恢复目标。
  - 备份完整性在切换前验证。
  - 空间不足、路径逃逸、摘要失败或备份不完整时停止事务。
  - 不在备份清单、日志和回执中记录密码、Token、Cookie 或私钥。
- **优先级**：必须
- **类型映射**：功能、安全
- **来源**：用户确认；3.0.0 参考设计

### FR-008：执行补偿式安装事务

- **描述**：当候选和备份均通过时，系统必须通过具有明确阶段和补偿恢复行为的事务执行部署。
- **验收标准**：
  - 阶段至少包括 `planned`、`candidate_validated`、`backed_up`、`switching`、`verifying`、`committed`、`rolled_back` 和 `recovery_required`。
  - 每次受管写入记录目标、旧摘要、新摘要、阶段和结果。
  - 单个受管根尽量使用局部原子切换。
  - 跨 Codex、Vault 和配置路径使用持久化事务日志和补偿恢复。
  - 任何切换后失败不得标记 `committed`。
  - 恢复完成后必须验证恢复目标摘要。
- **优先级**：必须
- **类型映射**：功能、安全、解决方案
- **来源**：用户确认

### FR-009：保留用户长期资产

- **描述**：当未来执行 4.0.0 干净安装时，系统必须保留或受控导入用户长期资产，但不得继承旧运行时授权状态。
- **验收标准**：
  - 支持导入 Vault 用户笔记、非受管模板、Workspace 注册、用户偏好、自定义 Agent 和自动化偏好。
  - 外部集成只保留模式和非敏感引用。
  - 不继承旧 Hook、Validator、临时委派绑定、回执、未完成事务和评审状态。
  - 导入行为具有来源、转换版本、结果和冲突记录。
  - 本次仓库阶段只通过测试 Fixture 验证，不读取本机真实资产。
- **优先级**：必须
- **类型映射**：用户、功能、过渡
- **来源**：用户确认

### FR-010：Doctor 一次聚合完整诊断

- **描述**：当执行 Doctor 时，系统必须运行所有安全且依赖条件满足的独立诊断，并一次聚合结果。
- **验收标准**：
  - 插件、当前 Skill、受管运行时、Agent、Hook、Validator、Vault、Workspace、自动化和 Playbook 分别由独立诊断器处理。
  - 一个诊断失败不得阻止其他独立诊断执行。
  - 依赖不足的诊断返回 `skipped` 和原因。
  - 每项诊断返回 facts、errors、warnings、remediation 和 runtime_checked。
  - Doctor 不直接修复问题。
  - 不存在自动 Doctor、修复、Doctor 循环。
- **优先级**：必须
- **类型映射**：用户、功能
- **来源**：用户确认；当前 Doctor 分析

### FR-011：区分部署和激活状态

- **描述**：当文件部署完成但当前 Codex 进程尚未确认加载新运行时时，系统必须明确表达后续激活状态。
- **验收标准**：
  - 至少区分 `files_installed`、`restart_required`、`trust_required`、`runtime_unverified`、`verified` 和 `recovery_required`。
  - 安装脚本完成不得直接等同于 `verified`。
  - Hook 变化时输出 `trust_required`；未变化时不得要求无意义重复信任。
  - 新根任务运行 Doctor 通过后才能标记 `verified`。
- **优先级**：必须
- **类型映射**：用户、功能
- **来源**：用户关于刷新、重启和 Hook 信任的历史反馈

### FR-012：重写 Hook 与 Validator 内部实现

- **描述**：当重写安全 Hook 和 Validator 时，系统必须保持现有安全不变量和薄入口。
- **验收标准**：
  - 重写前先建立行为契约测试。
  - 保留任务上下文 Schema、运行记录 Schema 和路由验证。
  - 保留根 Agent 保护、原子绑定消费、随机回执、转录证明和 Vault 写入校验。
  - 不能因拆分形成可绕过的检查窗口。
  - `SubagentStart` 输出必须符合当前 Codex Hook JSON 契约，同时提供 `hookEventName=SubagentStart` 和非空 `additionalContext`。
  - 运行时 Doctor 必须通过只读协议探针验证已部署 Hook 的响应结构，不能只凭 Hook 注册、信任状态和文件摘要判定委派链路可用。
  - Validator CLI 和 Hook 正常错误均使用结构化、可诊断输出。
- **优先级**：必须
- **类型映射**：功能、安全
- **来源**：用户确认；全局执行契约

### FR-013：建立 Manifest 驱动的第三方 Skill 治理

- **描述**：当 XiaoH 包含第三方 Skill 或吸收其方法时，系统必须通过可审计 Manifest 描述来源和决策，不得把全部清单硬编码在校验函数中。
- **验收标准**：
  - Manifest 包含仓库、固定提交、许可证、来源摘要和逐 Skill 决策。
  - `adapt_and_add` 项记录上游与改造后摘要。
  - `absorb_method` 项记录目标 Skill 和吸收理由。
  - `exclude` 项记录排除理由。
  - 上游提交变化时必须重新审核，不能继承旧数量或替换结论。
  - 校验器能够通用验证 Manifest，不硬编码每个 Skill 名称和文件摘要。
- **优先级**：必须
- **类型映射**：功能、治理
- **来源**：用户要求吸收 mattpocock/skills；代码分析

### FR-014：提供显式单次代码评审

- **描述**：当用户明确要求评审固定 Diff 时，系统可以运行一次规范轴和需求轴代码评审，但不得将其纳入默认开发门禁。
- **验收标准**：
  - 用户未明确请求时不得自动触发。
  - 必须固定 commit、branch、tag 或 merge-base。
  - 规范轴与需求轴分别输出，不能互相掩盖。
  - 没有需求来源时，需求轴明确标记不可用。
  - 评审结束后不自动修复、不自动重评、不创建 Campaign。
  - 确定性构建和测试结果仍是实现验收事实。
  - 如使用 Agent，必须遵守 XiaoH 正式委派门禁。
- **优先级**：应该
- **类型映射**：用户、功能
- **来源**：用户要求重新客观评估 mattpocock/skills

### FR-015：整理全部 XiaoH Skill

- **描述**：当 4.0.0 构建能力清单时，系统必须审核全部 Skill 的触发、职责、上下文成本和完成条件。
- **验收标准**：
  - 每个 Skill 有单一主要职责和清晰触发条件。
  - 模型自动触发与用户显式触发有明确区分。
  - 公共规则只有一个事实源。
  - 仅特定分支需要的内容通过引用渐进披露。
  - 删除重复、沉积、无效指令和纯别名 Skill。
  - 吸收 `writing-great-skills` 的质量原则。
  - 吸收 `handoff` 的引用、脱敏和未完成状态表达原则。
- **优先级**：必须
- **类型映射**：解决方案、功能
- **来源**：用户确认；mattpocock/skills 客观复评

### FR-016：提供稳定 CLI 和结构化响应

- **描述**：当用户调用 XiaoH CLI 时，系统必须通过薄入口调用应用用例并返回统一响应。
- **验收标准**：
  - 保留 plan、setup、update、doctor、workspace 和自动化相关命令概念。
  - 统一外壳包含 schema_version、status、operation、errors、warnings、actual_writes、unresolved_items 和 recovery_conditions。
  - 安装响应增加 transaction_id、phase、backup、recovery 和 activation_state。
  - CLI 不包含领域规则和事务状态转换。
  - 错误不以无上下文堆栈作为正常输出。
- **优先级**：必须
- **类型映射**：用户、外部接口、功能
- **来源**：用户确认；当前 CLI

### FR-017：完成仓库隔离验证

- **描述**：当开发和验证 4.0.0 时，系统必须只使用仓库和临时目录，不得修改真实本机运行时。
- **验收标准**：
  - 安装、更新、Doctor、自动化和用户资产导入测试全部使用临时路径或模拟 Adapter。
  - 测试不会写入真实 `~/.codex`、`~/.xiaoh` 或 Obsidian Vault。
  - 测试不会修改插件缓存或 Playbook CLI。
  - 验收产物明确标记为“可安装候选”，而不是“本机已安装”。
- **优先级**：必须
- **类型映射**：业务、安全、过渡
- **来源**：用户明确要求

### FR-018：删除旧生产实现

- **描述**：当新实现通过全部隔离验收时，仓库必须删除旧运行时生产实现，不得长期保留两套可执行路径。
- **验收标准**：
  - 所有公共入口只指向新实现。
  - 旧模块、死代码、兼容分支和旧评审资产被删除。
  - 搜索和依赖检查确认没有旧入口调用。
  - Git 历史继续提供回退能力，不在生产代码中保存废弃实现。
- **优先级**：必须
- **类型映射**：解决方案、过渡
- **来源**：用户要求全面重写

### FR-019：提供按风险收敛的通用编码流程

- **描述**：当 XiaoH 承担编码开发时，系统必须根据实际风险选择一条执行通道，并以确定性证据完成一次收敛，不得让低风险任务默认进入重型需求流程或自动代码评审。
- **验收标准**：
  - schema 1.6 任务上下文记录且只记录一个 `execution_lane`：`fast`、`standard` 或 `high_risk`。
  - `fast` 只允许低风险、局部、可逆、验收清楚且不产生新业务、接口、安全、数据、事务、迁移或兼容语义的改动；符合条件时允许 `artifact_route=direct_change`。
  - `standard` 使用适用的 OpenSpec 和影响面验证；`high_risk` 使用完整 Spec+RFC/OpenSpec 及适用的契约、安全、集成和恢复验证。
  - Agent 只有在用户已授权且存在明确的专业、并行或写入隔离收益时才可使用；执行通道本身不授予委派权限。
  - 验证从实际改动的接口、调用方、契约、数据/安全边界和构建依赖推导；未变化且仍新鲜的证据可以复用。
  - 首轮验证完成全部独立且安全的检查，形成一个完整失败集；按共同根因修复后只重跑受影响检查，最后执行通道收口门禁。
  - 完成记录包含改动范围、检查结果、未解决项和剩余风险的验证证据摘要。
  - 用户未明确请求时不得触发 `code-review`。
  - Validator 拒绝高风险任务降级到 `fast`、`high_risk` 使用非完整验证，以及无授权、无收益或无目标 Agent 的委派。
- **优先级**：必须
- **类型映射**：用户、解决方案、功能
- **来源**：用户对通用编码效率的确认与本次继续优化授权

### FR-020：把执行授权绑定到真实写入范围

- **描述**：产生代码或配置副作用前，根任务必须用当前任务上下文建立短时执行绑定；结束时必须用绑定前后的实际文件状态证明改动没有越过授权范围，也没有覆盖未明确接管的既有改动。
- **验收标准**：
  - 绑定包含任务标识、上下文摘要、允许路径、受管仓库、既有改动清单、创建与过期时间，并使用内容摘要防止漂移。
  - `apply_patch` 与明确可识别的写命令在执行前校验目标路径；没有绑定、绑定过期、上下文漂移或目标越界时失败关闭。
  - shell 命令解析只作为前置减险；最终以绑定前后 Git 状态和文件摘要形成的范围证明为准，不宣称能够完整理解任意 shell。
  - 范围证明列出任务实际新增、修改和删除的路径；越界路径或未授权接管的既有改动使收口失败。
  - 只读探索不要求写入绑定；语义选择仍由 XiaoH 与用户负责，不交给 Hook 判断。
- **优先级**：必须
- **类型映射**：权限、安全、解决方案
- **来源**：用户确认的门禁强化方案

### FR-021：把来源与验证结果绑定到可核验事实

- **描述**：任务上下文不得只声明来源和验证命令；来源必须带当前摘要，完成记录中的通过项必须指向可校验的执行证据并完整覆盖任务要求。
- **验收标准**：
  - 必需来源记录路径、用途、类型和 SHA-256；校验时发现缺失、摘要漂移或路径类型不符即失败。
  - 验证项具有稳定 ID、类别、命令、期望结果和必需标记；任务通道要求的类别必须被覆盖或提供明确不适用理由。
  - 完成记录通过项记录退出码、时间和证据文件摘要；命令、ID、类别和上下文必须与任务上下文一致。
  - 完成状态必须覆盖全部必需验证项，并引用通过的根执行范围证明；自述“passed”但缺少证据不能收口。
  - 校验器验证证据结构、摘要、覆盖和新鲜度，不把日志文本的业务含义冒充为自动证明。
- **优先级**：必须
- **类型映射**：安全、验证、解决方案
- **来源**：用户确认的门禁强化方案

## 4. 非功能需求

### NFR-001：安全与失败关闭

- **描述**：来源、路径、权限、候选、备份、事务、绑定或证据无法验证时，系统必须停止相关副作用并返回明确失败。
- **测量方法**：为路径逃逸、符号链接、摘要漂移、绑定过期、角色不匹配、敏感数据和候选来源失败建立负向测试。
- **优先级**：必须
- **来源**：全局执行契约；用户确认

### NFR-002：可恢复性

- **描述**：第一次受管写入后发生的故障必须能够恢复，或明确进入需要人工处理的状态。
- **测量方法**：对每个事务阶段执行故障注入；验证 `rolled_back` 或 `recovery_required` 状态及目标摘要。
- **优先级**：必须
- **来源**：用户确认

### NFR-003：幂等性

- **描述**：相同输入重复执行不得产生重复 Agent、重复 Hook、重复自动化、重复配置块或无意义内容漂移。
- **测量方法**：连续执行两次 setup、update、Doctor 和自动化对账，比较文件摘要和响应。
- **优先级**：必须
- **来源**：参考设计；用户确认

### NFR-004：可测试性

- **描述**：文件系统、进程、时钟、插件管理器和自动化存储必须通过 Ports/Adapters 替换。
- **测量方法**：核心规则单元测试不依赖用户目录、真实 Codex 或外部命令。
- **优先级**：必须
- **来源**：全面重写目标

### NFR-005：可观测性

- **描述**：计划、事务、恢复、Doctor 和激活状态必须输出结构化证据。
- **测量方法**：验证每次实际写入、状态转换、失败和恢复都可从回执定位；不记录敏感值。
- **优先级**：必须
- **来源**：用户对重复排查和状态不透明的反馈

### NFR-006：模块深度与变更局部性

- **描述**：模块必须以小接口隐藏内部复杂度，常见变化不应同时修改多个无关模块。
- **测量方法**：依赖方向检查、公开接口审查、循环依赖检测和典型变更影响分析。
- **优先级**：必须
- **来源**：模块化参考；用户确认

### NFR-007：跨平台

- **描述**：运行时不得依赖 macOS 专属路径或文件系统语义。
- **测量方法**：macOS、Windows 和受支持 Python 版本执行语法、单元、集成、隔离安装和入口测试。
- **优先级**：必须
- **来源**：3.1.2 当前兼容范围

### NFR-008：确定性验证

- **描述**：构建、类型检查、lint、单元测试、契约测试和集成测试不得以主观评审代替。
- **测量方法**：CI 中适用门禁全部必须通过；不得以 `continue-on-error` 掩盖失败。
- **优先级**：必须
- **来源**：用户对多轮评审低效的反馈

### NFR-009：本机零副作用

- **描述**：代码重写和验收阶段不得修改当前用户运行环境。
- **测量方法**：测试前后核对真实 XiaoH、Codex 和 Vault 受管路径摘要；生产安装入口不得在本阶段被调用。
- **优先级**：必须
- **来源**：用户明确要求

### NFR-010：最小外部依赖

- **描述**：新运行时优先使用 Python 标准库和 Codex 原生能力，不为内部抽象引入无必要依赖或服务。
- **测量方法**：依赖清单审查；新增依赖必须有功能、安全或跨平台必要性证据。
- **优先级**：应该
- **来源**：全面重写目标；实现阶段最小化约束

### NFR-011：流程收敛效率

- **描述**：编码流程必须按风险增加成本，避免重复读取未变化上下文、重复执行无关检查或把再次评审作为失败修复步骤。
- **测量方法**：契约测试覆盖三档通道、直接改动、Agent 收益门槛和验证摘要；流程文本要求一次完整失败集、根因分组、受影响重跑和最终单次收口。
- **优先级**：必须
- **来源**：用户对重复评审、重复修复和耗时问题的反馈

### NFR-012：证据不可仅靠自我声明

- **描述**：影响权限、范围和完成结论的关键证据必须具有可复算摘要、上下文绑定与时间边界，不能只依赖自然语言或状态字符串。
- **测量方法**：负向测试覆盖伪造通过状态、缺失日志、日志摘要漂移、来源摘要漂移、任务上下文漂移、过期绑定和实际越界改动。
- **优先级**：必须
- **来源**：门禁可执行性审计

## 5. 外部接口需求

### IF-001：XiaoH CLI

- **类型**：系统集成
- **端点/入口**：`plugins/xiaoh/scripts/xiaoh.py`
- **请求/响应/交互**：解析 plan、setup、update、doctor、workspace 和自动化命令，调用应用层并输出统一 JSON 或人类可读结果。
- **错误处理**：参数错误、路径错误和用例错误转换为稳定响应与退出码，不泄漏无上下文堆栈。
- **来源**：FR-005、FR-016

### IF-002：Codex 插件管理器

- **类型**：系统集成
- **端点/入口**：Codex 插件列表、启用状态和候选来源事实。
- **请求/响应/交互**：只有显式请求运行态证据时，才读取并返回插件身份、版本、启用状态和来源等安全字段。不得输出插件缓存路径或原始敏感字段；插件安装和缓存切换仍由插件管理器负责。
- **错误处理**：来源不可验证时返回 `unverified` 或 `failed`；不得通过缓存自比较伪造成功。
- **来源**：FR-006、FR-018

### IF-003：本地文件系统

- **类型**：系统集成
- **端点/入口**：Codex Home、XiaoH 配置、Obsidian Vault、测试临时根。
- **请求/响应/交互**：所有路径通过 Filesystem Port 访问；安装计划与测试显式传入根路径。
- **错误处理**：路径逃逸、符号链接风险、权限失败、空间不足和摘要失败均停止相关写入。
- **来源**：FR-005 至 FR-009、NFR-001

### IF-004：Hook 信任与运行时验证

- **类型**：系统集成
- **端点/入口**：Codex Hook 信任界面、新根任务 Doctor。
- **请求/响应/交互**：文件变化后输出 `restart_required` 和 `trust_required`；用户人工重启和信任后，通过运行时 Doctor 核对 Hook 注册、信任、文件摘要和 `SubagentStart` 响应协议。
- **错误处理**：未信任或当前进程未加载时不得标记 `verified`。
- **来源**：FR-011、FR-012

### IF-005：Obsidian Vault

- **类型**：系统集成
- **端点/入口**：用户配置指定的唯一 Vault 路径。
- **请求/响应/交互**：读写前重新解析真实路径，通过 Vault Hook，并区分用户文件与受管模板。
- **错误处理**：用户定制冲突不得静默覆盖；路径或权限不可信时失败关闭。
- **来源**：FR-004、FR-009

### IF-006：托管自动化

- **类型**：系统集成
- **端点/入口**：Codex 自动化存储 Adapter。
- **请求/响应/交互**：按逻辑身份对账任务、保留用户偏好、更新模板并读回验证。
- **错误处理**：能力不可用时标记 `pending` 或 `degraded`，不伪造绑定，不重复创建。
- **来源**：FR-004

### IF-007：Playbook

- **类型**：系统集成
- **端点/入口**：Playbook worker/status 只读命令。
- **请求/响应/交互**：仅在配置为受管集成时读取 worker 和任务状态证据。
- **错误处理**：版本异常只报告证据和人工建议；不得执行版本变更。
- **来源**：FR-001、FR-004；全局 Playbook 边界

### IF-008：第三方 Skill Manifest

- **类型**：系统集成
- **端点/入口**：插件内第三方来源及决策 Manifest。
- **请求/响应/交互**：本地读取固定来源、许可证、提交、文件摘要和决策证据。
- **错误处理**：Schema、摘要、路径或来源不一致时失败；不得自动从网络覆盖。
- **来源**：FR-013、FR-015

### IF-009：任务执行与收口证据

- **类型**：系统集成
- **端点/入口**：schema 1.6 任务上下文、schema 1.2 运行记录、`xiaoh-core` 与 `xiaoh-requirement-routing`
- **请求/响应/交互**：任务上下文记录通道、验证范围、影响面和委派决策；运行记录输出一次验证证据摘要。
- **错误处理**：风险与通道不一致、直接改动包含风险信号、委派缺少授权/收益/目标 Agent 或完成记录缺少摘要时校验失败。
- **来源**：FR-019、NFR-011

### IF-010：根任务执行绑定与范围证明

- **类型**：Codex Hook 与 Validator 集成
- **端点/入口**：根任务写入 Hook、执行绑定准备/证明入口、schema 1.6 任务上下文和 schema 1.2 运行记录。
- **请求/响应/交互**：副作用前准备一次短时绑定；Hook 校验可识别目标；完成前生成绑定前后差异证明；Validator 对上下文、来源、验证证据和范围证明做一致性校验。
- **错误处理**：缺失、过期、漂移、路径越界、既有改动冲突、验证证据缺失或摘要不符时失败关闭；只读动作保持可用。
- **来源**：FR-020、FR-021、NFR-012

## 6. 过渡需求

### TR-001：冻结 3.1.2 产品行为基线

- **描述**：重写前必须把需要保留的 3.1.2 产品行为转换为契约测试。
- **策略**：按根身份、CLI、Agent、Skill、Hook、Validator、Workspace、Vault、自动化和 Playbook 分组建立测试。
- **回滚计划**：如果新实现无法满足基线，保持当前稳定代码，不切换公共入口。
- **来源**：FR-001、FR-012

### TR-002：仓库内分阶段替换

- **描述**：开发期间允许新实现与旧实现暂时共存，但不得形成两个长期生产入口。
- **策略**：新实现先通过隔离测试；公共入口切换后删除旧实现。
- **回滚计划**：公共入口切换前通过 Git 回退当前批次；切换后若验收失败，回退整个候选提交。
- **来源**：FR-003、FR-018

### TR-003：3.1.2 用户资产导入能力

- **描述**：4.0.0 不兼容旧运行时，但必须提供未来干净安装所需的用户长期资产导入逻辑。
- **策略**：使用测试 Fixture 建立 3.1.2 用户资产样本并验证转换。
- **回滚计划**：导入失败时不修改来源资产，目标候选丢弃或通过事务恢复。
- **来源**：FR-009

### TR-004：生成可安装候选版本

- **描述**：代码、测试和文档完成后形成可安装候选，但不部署到当前机器。
- **策略**：输出版本、测试证据、已知限制和未来安装前置条件。
- **回滚计划**：候选不影响当前运行时；通过 Git 删除或修订候选。
- **来源**：FR-017

### TR-005：未来本机安装单独授权

- **描述**：实际安装、重启、Hook 信任和运行时 Doctor 不属于本次授权。
- **策略**：只有用户以后明确授权时才制定并执行本机安装步骤。
- **回滚计划**：未来安装必须使用本 Spec 定义的恢复清单和补偿事务。
- **来源**：用户明确要求

## 7. 约束与假设

### 7.1 技术约束

- 目标版本为 XiaoH 4.0.0。
- 不保留 2.x 或 3.1.2 内部运行时兼容代码。
- 不兼容旧安装状态、事务证据和内部 Schema。
- 保留 3.1.2 产品能力和用户长期资产导入语义。
- Python 版本支持范围不得因重写无来源提高。
- 优先使用标准库。
- 不修改 Codex 插件缓存。
- 不修改 Playbook CLI。
- 不自动信任 Hook。
- 安全 Hook 和 Validator 必须先有契约测试。
- 不涉及 UI 或浏览器页面。

### 7.2 业务约束

- 本阶段不安装本机。
- 不恢复旧代码评审 Campaign。
- 代码评审只能显式、单次运行。
- 确定性验证是实现验收事实源。
- 不建立第二套 Workspace、项目历史、需求或任务状态机。
- 不把可选 Issue Triage 放入 4.0.0 核心范围。
- 不因全面重写删除用户已确认功能。
- 低风险不等于免验证；快速通道必须保留可运行的影响面检查。
- 执行通道不构成 Agent 委派授权。

### 7.3 假设

- 当前 3.1.2 代码和已确认讨论足以建立产品行为基线。来源：已验证。
- 真实安装目标可能跨多个文件系统，因此采用补偿事务比宣称全局原子事务更准确。来源：代码路径与文件系统事实。
- Codex 插件管理器继续提供插件身份和候选来源事实。来源：当前集成。
- CI 可继续提供 macOS 和 Windows 环境。来源：当前工作流。
- mattpocock/skills 当前固定审计提交可作为 4.0.0 初始来源基线；发布前仍需重新核对。来源：当前审计清单。
- 未来本机安装会由用户单独授权。来源：用户确认。

## 9. 变更/设计提案（RFC）

### 9.1 现状分析

- **当前架构**：运行时已拆为若干 Python 文件；CLI 启动器和 Validator 入口较薄；配置、Workspace、自动化和 Vault 已有独立模块；Doctor、安装器和插件状态仍承担较多编排与规则。
- **当前问题**：星号导入模糊依赖；`plugin_state.py` 混合多个变化原因；Doctor 存在首错停止；安装器没有候选和自动恢复；计划与回执缺少完整写入证据；Skill 治理硬编码；测试以正常路径为主。
- **当前流程问题**：评审循环已经移除，但所有编码任务仍缺少明确的风险分流、直接改动边界、Agent 收益门槛和一次性失败收敛契约。
- **相关代码路径**：
  - `plugins/xiaoh/xiaoh_runtime/install.py`
  - `plugins/xiaoh/xiaoh_runtime/doctor.py`
  - `plugins/xiaoh/xiaoh_runtime/plugin_state.py`
  - `plugins/xiaoh/xiaoh_runtime/vault_runtime.py`
  - `plugins/xiaoh/xiaoh_runtime/automation.py`
  - `tests/test_clean_break_312.py`

### 9.2 目标状态

- **提议架构**：采用领域层、应用层、Ports、Adapters、安装生命周期、独立诊断器和薄接口层。
- **关键变更**：
  - 所有外部副作用通过 Port。
  - 安装采用候选与补偿事务。
  - Doctor 只聚合独立诊断器。
  - Skill 治理由 Manifest 驱动。
  - CLI 只解析、调用和格式化。
  - Hook 与 Validator 在契约保护下重写。
  - 代码评审成为显式单次能力。
  - 旧实现最终完全删除。

#### 数据模型

`InstallationPlan` 包含：schema_version、operation、source_version、target_version、paths、asset_inventory、conflicts、expected_writes、expected_deletes、preserved_assets、candidate_requirements、backup_requirements、unresolved_items 和 recovery_conditions。

`RecoveryManifest` 包含：schema_version、transaction_id、created_at、items 和 completeness_status。每个 item 包含 asset_type、source、backup_path、restore_target、digest 和 size。

`InstallationTransaction` 包含：schema_version、transaction_id、operation、phase、started_at、updated_at、planned_writes、actual_writes、errors、recovery_actions 和 result。

`DiagnosticResult` 包含：diagnostic_id、status、facts、errors、warnings、skipped_reason、remediation、runtime_checked 和 duration_ms。

`DoctorReport` 包含：schema_version、status、effective_status、installation_status、activation_state、diagnostics、errors、warnings 和 unresolved_items。

`SkillSourceAudit` 包含：schema_version、source、license、audit、comparison_dimensions、decisions 和 decision_evidence。

`RootExecutionBinding` 包含：schema_version、task_id、task_context、context_hash、session_id、allowed_paths、preexisting_changes、repositories、created_at、expires_at、nonce 和 binding_hash。每个 repository 基线包含 root、HEAD 及 dirty/untracked 文件状态与摘要。

`VerificationEvidence` 包含：schema_version、task_id、context_hash、binding_hash、verification_id、category、command、expected、exit_code、started_at、ended_at 和 output_sha256。原始 stdout/stderr 不写入证据。

`RootScopeProof` 包含：schema_version、task_id、context_hash、binding_hash、status、changed_paths、scope_violations、preexisting_change_violations、repository_heads 和 attested_at。

#### 主流程

安装正常流程：

```text
解析路径
→ 读取配置
→ 分类资产
→ 生成计划
→ 构建隔离候选
→ 校验候选
→ 生成恢复清单
→ 完成备份并验证摘要
→ 创建事务记录
→ 分根切换受管内容
→ 写入配置和状态
→ 执行静态 Doctor
→ 提交事务
→ 输出 restart_required / trust_required / runtime_unverified
```

安装失败流程：

```text
第一次写入前失败
→ 丢弃候选
→ 返回 failed
→ 不执行恢复

第一次写入后失败
→ 停止后续写入
→ 读取事务和恢复清单
→ 反向恢复已写入目标
→ 验证恢复摘要
→ 返回 rolled_back

恢复不完整
→ 保留事务和备份
→ 返回 recovery_required
→ 不宣称安装成功
```

Doctor 流程：

```text
解析请求
→ 构造独立诊断集合
→ 执行所有依赖满足且安全的诊断
→ 对依赖不足项标记 skipped
→ 聚合 facts / errors / warnings
→ 计算安装状态和激活状态
→ 返回一次性完整报告
```

代码评审流程：

```text
用户显式请求
→ 固定比较点
→ 确认 Diff 非空
→ 定位规范与需求来源
→ 分别执行规范轴和需求轴分析
→ 汇总但不互相重排
→ 返回一次结果
→ 停止
```

第三方 Skill 更新流程：

```text
发现新的上游提交
→ 固定新提交
→ 重新获取许可证和文件摘要
→ 对每个正式 Skill 重新比较
→ 重新决定 adapt / absorb / exclude / replace
→ 更新 Manifest
→ 验证改造后 Skill
→ 不自动覆盖已审核内容
```

通用编码流程：

```text
确认目标与当前事实
→ 选择 fast / standard / high_risk
→ 选择 direct_change / OpenSpec / Spec+RFC+OpenSpec
→ 判断 Agent 是否已授权且有实质收益
→ 校验来源摘要并准备根执行绑定
→ 在绑定范围内实现最小根因改动
→ 通过绑定入口执行影响面或完整验证，形成一次完整失败集
→ 按共同根因修复并重跑受影响检查
→ 从真实 Git 前后状态生成范围证明
→ 执行通道收口门禁
→ 输出一次验证证据摘要
→ 停止；除非用户明确要求，不进入代码评审
```

### 9.4 考虑的替代方案

| 选项 | 优点 | 缺点 | 决策 |
|---|---|---|---|
| A：继续修补 3.1.2 模块 | 短期改动较少 | 循环依赖、职责混合和安装流程债务继续存在 | 已拒绝 |
| B：全面重写内部实现，保留产品能力 | 可重新建立正确边界、事务和诊断模型 | 初始实现和验证成本较高 | 已选 |
| C：同时保留旧新运行时兼容 | 迁移表面平滑 | 双实现、双 Schema 和恢复逻辑复杂 | 已拒绝 |
| D：删除全部旧功能后从最小核心开始 | 实现最快 | 不满足保留既有能力的目标 | 已拒绝 |
| E：将运行时改成远程服务 | 可集中管理 | 引入网络、认证、服务运维和隐私风险 | 已拒绝 |
| F：宣称跨全部路径全局原子安装 | 概念简单 | 不符合跨文件系统事实 | 已拒绝 |
| G：局部原子切换加跨根补偿事务 | 行为真实、可恢复、可验证 | 需要事务日志和恢复实现 | 已选 |
| H：恢复旧自动代码评审门禁 | 看似严格 | 重新引入多轮循环和高时间成本 | 已拒绝 |
| I：显式单次代码评审 | 保留 Diff 评审价值且不影响默认流程 | 需要严格触发边界 | 已选 |
| J：所有编码任务统一使用完整需求与全量验证 | 规则单一 | 小改动成本过高，重复上下文与无关检查多 | 已拒绝 |
| K：仅依赖模型自行判断流程深度 | 文档和代码改动最少 | 判断不可追溯，容易误降级或过度执行 | 已拒绝 |
| L：工件路由与三档执行通道正交，并由 Validator 约束关键降级 | 兼顾效率、安全和可验证性 | 任务上下文增加少量字段 | 已选 |

选项 B、G、I、L 能完整覆盖已确认目标，同时避免旧兼容、评审状态机、统一重流程和不真实原子性带来的长期复杂度。

### 9.6 实施与迁移计划

- **实施顺序**：
  1. 固定 3.1.2 产品能力与安全契约测试。
  2. 建立新 domain、ports、adapters 和接口响应结构。
  3. 建立依赖方向和禁止星号导入门禁。
  4. 重写插件事实、配套能力和 Skill 治理。
  5. 重写独立诊断器和 Doctor 聚合。
  6. 重写安装计划、候选、备份、事务和恢复。
  7. 重写配置、Workspace、Vault 和自动化。
  8. 在契约保护下重写 Hook 和 Validator。
  9. 切换 CLI 公共入口。
  10. 整理全部 Skill，引入受限版代码评审。
  11. 执行故障注入、幂等和跨平台测试。
  12. 删除旧实现和旧评审残留。
  13. 形成 4.0.0 可安装候选。
  14. 停止，不安装本机。
  15. 加入三档执行通道、直接改动门槛、Agent 收益门槛和收敛式验证证据。
  16. 加入根执行绑定、委派路径隔离、受控验证证据和真实 Git 范围证明。
- **风险缓解**：
  - 功能倒退：先固定行为契约和能力清单。
  - 安全门禁削弱：Hook 和 Validator 先测试后替换。
  - 新旧实现语义漂移：以确认的产品行为而非旧内部结构为准。
  - 事务恢复缺陷：对每个写入阶段执行故障注入。
  - 跨平台路径问题：使用 Ports/Adapters 和真实 CI。
  - Skill 触发膨胀：区分显式调用并执行 Skill 质量审核。
  - 代码评审重新形成循环：在 Skill 与契约中禁止自动修复和重评。
  - 快速通道被滥用：Validator 限定低风险、影响面验证和无风险信号；发现新语义时立即升级。
  - Agent 使用反而增加协调成本：要求用户授权、实质收益和明确目标 Agent 同时成立。
  - 误写本机：所有集成入口显式传入临时测试路径，本阶段不调用生产安装入口。
- **测试策略**：
  - 单元测试：状态转换、资产分类、摘要、路径安全、配置合并、Workspace、Doctor 聚合、Skill Manifest。
  - 契约测试：CLI、JSON Schema、Agent、Skill、Hook、Validator、Vault 用户定制和 Playbook 边界。
  - 流程契约测试：三档通道、直接改动、委派门槛、来源摘要、验证证据、写入范围和完成证明。
  - 集成测试：临时 Codex Home、Vault、配置、自动化和模拟插件管理器。
  - E2E 测试：临时目录中的完整 plan、candidate、backup、switch、doctor、receipt。
  - 故障测试：候选、备份、切换、配置、Vault、Doctor 和恢复中断。
  - 幂等测试：重复 setup、update、Doctor 和自动化对账。
  - 跨平台测试：macOS、Windows 和受支持 Python。
  - 质量门禁：类型检查、lint、语法、构建和测试不得忽略失败。
- **回滚计划**：
  - 公共入口切换前，按提交回退当前实现批次。
  - 公共入口切换后但最终验收前，回退整个候选提交。
  - 仓库重构不写真实本机，因此代码回滚不涉及本机恢复。
  - 未来真实安装使用 RecoveryManifest 和 InstallationTransaction 执行恢复。
