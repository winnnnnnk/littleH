# 工程方案双轨决策

## 目标

在存在真实工程取舍时，同时构造并比较：

1. **最小改动方案**：尽量复用现有结构，以较小实施范围满足目标。
2. **最合适改动方案**：按正确的领域语义、职责归属和生命周期完整承载目标。

最小改动不是默认答案。先判断哪种方案更适合业务，再由用户选择；如果两种方案在当前约束下实质一致，明确说明它们已经收敛，不虚构差异。

## 工作流

### 1. 固定目标结果

先从需求、已确认决策和可观察验收结果中提取：

- 当前必须实现的业务结果；
- 明确要求保持不变的兼容行为；
- 已确认的后续演进；
- 安全、合规、数据生命周期和运维约束。

不要用当前代码的限制反向缩小已确认目标，也不要把未经确认的未来可能性当成必做范围。

### 2. 获取目标系统证据

沿真实调用链确认入口、数据流、持久化、校验、错误处理和测试。对字段或旧结构能否复用，至少核对：

- 字段语义和所有者；
- 写入者、读取者及其他业务用途；
- 唯一性、长度、编码、空值和索引约束；
- 生命周期、失效、覆盖和并发行为；
- 数据迁移与旧数据兼容；
- 安全边界和审计要求。

结论必须标记为以下之一：

- **已证实不可用**：存在直接代码、模型、约束或运行证据；
- **满足条件可用**：约束明确，满足条件即可采用；
- **风险待确认**：目前只有可能性，缺少决定性证据；
- **推荐做法**：基于完整比较后的工程建议。

不得把“风险待确认”直接写成“不能用”。

### 3. 判断是否存在双方案

出现以下任一差异时，应提供两个方案：

- 目标覆盖度不同；
- 数据或职责归属不同；
- 生命周期、并发或安全行为不同；
- 兼容、迁移或回滚成本不同；
- 短期成本与长期维护收益不同。

如果这些维度没有实质差异，说明两种方案为何收敛，只保留一个实施建议。

### 4. 构造最小改动方案

说明：

- 复用哪些现有组件、字段或流程；
- 修改哪些模块和数据；
- 能完整覆盖哪些目标；
- 覆盖上限、隐含耦合、兼容风险和技术债；
- 验证与回滚方式。

“文件少、代码少”本身不是充分理由。

### 5. 构造最合适改动方案

说明：

- 功能应归属哪个模块、对象或数据模型；
- 如何表达正确的领域语义和生命周期；
- 需要修改的接口、数据库、配置、权限、迁移与测试；
- 实施、运维和迁移成本；
- 对当前目标和已确认演进的长期收益。

不要借“最合适”之名扩张到未经确认的通用平台或预防性架构。

### 6. 同维度比较并推荐

至少比较：

| 维度 | 最小改动方案 | 最合适改动方案 |
| --- | --- | --- |
| 目标结果覆盖度 |  |  |
| 领域语义与职责归属 |  |  |
| 数据生命周期与安全 |  |  |
| 兼容、迁移与回滚 |  |  |
| 可验证性与运维 |  |  |
| 实施成本与长期成本 |  |  |

给出明确推荐、证据和放弃另一方案的代价。推荐不替代用户对业务结果的选择。

### 7. 记录选择并继续

当两方案会产生不同业务结果、数据边界或长期承诺时，向用户提出一个具体选择问题。用户选定后，把选择和理由写入需求、Spec、OpenSpec、RFC 或 ADR 等适用事实源，并继续所有已授权的低风险工作。

只有出现新事实冲突、权限边界或需求变化时才重新确认。

## 与最小化工具的关系

需求分析、业务建模、方案比较和设计阶段不启用 Ponytail，也不以其“最少实现”规则约束方案判断。这个阶段应独立完成最小改动与最合适改动的双轨比较。

用户选定方案并进入实际代码编写、修改、重构、缺陷修复或测试代码编写后，再启用 Ponytail，在已确认边界内优先复用现有能力、标准库和原生能力，减少无必要抽象、样板与依赖。

Ponytail 只收敛实现，不能推翻选定方案，不能缩减已确认需求，也不能简化安全、正确性、兼容、错误处理、数据生命周期、可观测性和验证要求。实现阶段结束后停止应用，避免其偏置回流到后续需求和设计裁决。

## 输出要求

输出顺序固定为：

1. 结论与推荐；
2. 已确认事实与待确认风险；
3. 两方案对比，或两方案收敛的依据；
4. 推荐理由和选择后的影响；
5. 仅在结果存在实质差异时请求用户选择。
