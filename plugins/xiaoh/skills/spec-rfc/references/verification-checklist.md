# 验证检查清单

在提交 Spec+RFC 给用户确认前，必须完成以下两项检查。

---

## 1. 需求质量检查（13 项）

逐项检查并给出结论：

| # | 维度 | 检查内容 | 状态 |
|---|------|---------|------|
| 1 | 完整性 | 所有已知需求已记录；遗漏标记为 TBD | ✅/⚠️/❌ |
| 2 | 一致性 | 无内部矛盾 | ✅/⚠️/❌ |
| 3 | 正确性 | 反映利益相关者意图和已确认的澄清 | ✅/⚠️/❌ |
| 4 | 可行性 | 在已知约束下现实可行 | ✅/⚠️/❌ |
| 5 | 必要性 | 每个需求映射到明确的目标或理由 | ✅/⚠️/❌ |
| 6 | 优先级 | 存在明确的优先级 | ✅/⚠️/❌ |
| 7 | 可追溯性 | 唯一的 ID 和到源的链接 | ✅/⚠️/❌ |
| 8 | 无歧义性 | 避免模糊术语；行为被精确描述 | ✅/⚠️/❌ |
| 9 | 可验证性 | 需求是客观可测试的 | ✅/⚠️/❌ |
| 10 | 准入完整性 | Spec 准入门槛已检查；阻塞项已关闭或标为风险接受 | ✅/⚠️/❌ |
| 11 | 共享语言 | 关键术语已整理为 `CONTEXT.md` 候选项；无新增时已说明 | ✅/⚠️/❌ |
| 12 | ADR 判断 | 长期架构决策已判断是否需要 ADR；保存目录未被擅自假定 | ✅/⚠️/❌ |
| 13 | 前后端闭环验证 | 涉及 UI/前后端联动时，已写明浏览器验证路径、访问说明、登录角色、操作步骤、通过标准，且未保存真实凭据 | ✅/⚠️/❌ |

对于 ⚠️ 和 ❌ 的项目，说明具体问题和建议的解决方式。

---

## 2. "足够好"评估（3 个维度）

沿着三个维度推理 Spec 的"足够好"程度：

### 维度一：信息类型

确认 Spec 涵盖了：
- [ ] 功能需求
- [ ] 非功能需求 / 质量属性
- [ ] 设计和实现约束
- [ ] 业务规则
- [ ] 外部接口需求
- [ ] 数据类型和数据源
- [ ] 共享语言候选项（领域术语、缩写、状态、业务动作、边界规则）
- [ ] ADR 候选项或无需 ADR 的理由

判断：是否有缺失的信息类型会阻碍安全实施？还是可以作为 TBD 保留并带有可接受的风险？

### 维度二：知识广度

- 范围覆盖：是全范围还是部分范围迭代？
- 用户需求：高优先级的已包含？还是全部已包含？
- 质量属性：关键的已覆盖？还是全部已覆盖？
- 隐含/假设需求：是否识别并处理了？（记录 / 标记为风险 / 与用户确认排除）

### 维度三：细节深度

- [ ] 关键功能的正常流程已记录
- [ ] 关键功能的异常/错误处理已记录
- [ ] 非功能需求有可衡量的指标（负载、响应时间等）
- [ ] 每个需求足够精确，可以被验证和实施
- [ ] 所有阻塞性澄清项已关闭，或已进入带风险 TBD 模式并记录影响
- [ ] ADR 候选项包含背景、决策、备选方案、后果，且保存目录为用户确认项
- [ ] 涉及 UI/前后端联动时，已包含 Codex app 内嵌浏览器或 `webapp-testing` 可执行的闭环验证路径

---

## 输出格式

```
## 验证报告

### 需求质量
| 维度 | 状态 | 说明 |
|------|------|------|
| 完整性 | ✅ | [说明] |
| ... | ... | ... |

### 足够好评估
- **信息类型**: [评估结论] — [理由]
- **知识广度**: [评估结论] — [理由]
- **细节深度**: [评估结论] — [理由]

### 结论
[Spec+RFC 是否"足够好"可以继续？如果不，下一步是什么？]
```

---

## "不够好"时的处理

如果验证发现不够好：
1. 明确列出缺失或不充分的具体项
2. 给出两种选择：
   - **补充澄清**：向用户提问获取缺失信息（推荐）
   - **带风险前进**：标记为 TBD，在实施中处理
3. 由用户决定如何处理

如果用户选择"带风险前进"，记录风险确认：
```
## 风险与歧义确认
以下项存在歧义或未确认：
- TBD-X: [具体内容] — 潜在影响: [说明]
- TBD-Y: [具体内容] — 潜在影响: [说明]

用户已确认接受上述风险，继续实施。
```
