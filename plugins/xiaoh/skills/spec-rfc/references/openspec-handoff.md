# OpenSpec 工作流衔接

如果用户使用 OpenSpec 工作流，按以下规则衔接。

---

## 保存策略

用户确认 Spec+RFC 后：

1. 询问用户是否需要保存为 `.md` 文件
2. 如果保存，询问文件路径；未指定时默认 `docs/spec-rfc/<change-name>.md`
3. 保存时必须在文档顶部写入 `文档生成时间` 和 `生成方式：spec-rfc`
4. 修订已保存文档时，必须保留原 `文档生成时间`，并新增或更新 `最近修订时间`
5. 时间格式使用 `yyyy-MM-dd HH:mm:ss 时区`，优先使用当前运行环境时区
6. 如果不保存，已确认的内容仍可作为上下文使用

---

## OpenSpec 交接规则

### 输入边界

- 统一 Spec+RFC 文档是后续交接的需求上下文
- 进入 OpenSpec 后，artifact 结构、字段和顺序以 OpenSpec schema 为准
- Spec+RFC 提供需求背景、范围、约束和设计意图；不替代 OpenSpec 的模板
- 该文档将作为 OpenSpec change 的输入上下文；OpenSpec artifact 结构以 OpenSpec schema 为准。

### 交接流程

1. 显式调用 OpenSpec skill 或 CLI 流程（如 `openspec-new-change`）
2. `proposal.md`、`design.md`、`specs/*/spec.md`、`tasks.md` 的结构以 `openspec status` 和 `openspec instructions <artifact-id> --change ...` 返回的 schema 为准
3. Spec+RFC 文档与 OpenSpec 模板冲突时，artifact 格式以 OpenSpec 为准
4. 如发现 Spec+RFC 中存在关键缺口，先回到澄清流程，不直接编造 OpenSpec 内容

### tasks 拆分纪律

- 优先使用可端到端证明一个行为的 tracer-bullet 垂直切片，不按“先写全部模型、再写全部接口、最后补测试”的水平层次拆分。
- 为任务记录明确 blocking edges；只有真正依赖前置结果的任务才阻塞。
- 先处理会阻塞多个后续切片的基础风险、未知接口和迁移前置条件。
- `tasks.md` 只描述实施与验证顺序，不创建与 OpenSpec、XiaoH 任务上下文或 Playbook 竞争的状态机。
- 每个任务应能追溯到 Requirement/Scenario，并包含适用测试或验证证据。

### 需求变更处理

如果后续需求发生变化：
1. 优先更新统一 Spec+RFC 文档
2. 重新进入或继续 OpenSpec 工作流
3. 同步受影响的 artifact

---

## 确认流程

Spec 和 RFC 作为一个单一连贯工件一起呈现和确认。

### 呈现

1. 完整输出 Spec+RFC（所有 10 个章节，**不摘要、不省略、不用"如上所述"**）
2. 所有细节包括在内：代码片段、图表（以文本形式）、数据模型、API 定义
3. 最后一节必须为 TBD 列表，内容完整未被截断

### 请求确认

```
## Spec+RFC 确认

### 1. 授权
- [ ] 你是否接受此 Spec+RFC？

### 2. 保存偏好
- [ ] 是否保存为 Markdown 文件？
- [ ] 文件路径？

### 3. TBD 项目
[列出所有需要用户输入的 TBD]

### 4. 下一步
确认后：
1. 按选择保存文件
2. 如需进入 OpenSpec，移交给 OpenSpec 流程

说明：该文档将作为 OpenSpec change 的输入上下文；OpenSpec artifact 结构以 OpenSpec schema 为准。

💡 如有补充信息，请直接说明。
```

### 修订

用户请求修改时：
1. 根据反馈更新 Spec+RFC
2. 完整输出修订版（不得比前一版更短，除非用户明确要求删减）
3. 修订后重新走确认流程

### 确认前完整性检查

在任何确认请求前验证：
- 10 个章节完整
- 最后一节为 TBD 列表
- TBD 列表内容完整未被截断
- 修订版长度与前一版相当

明确告知用户："Spec+RFC 包含 10 个章节，最后一节为 TBD 列表，内容完整。"

---

## 实施阶段

用户授权开发后：

- 持续推进到完成，尽量减少中途暂停
- 遇到技术选择，基于 Spec 中的约束自行决策；只影响架构或业务逻辑的才回问用户
- 遇到阻塞先尝试替代方案，无法解决的在完成后一并告知
- 遵守 Spec 中的约束和 NFR；如遇冲突，优先回到 Spec 澄清
- 完成标准：所有 FR 已实现、构建成功、测试通过（或用户明确取消）

### 带风险的早期开发

如果 Spec+RFC 还不够好，但用户想提前开始：

1. **解释风险**：用具体的推理解释缺少什么或模棱两可，以及这会带来什么影响
2. **提出最小澄清**：给出可以显著降低风险的最少额外问题
3. **用户坚持时**：输出以下风险确认文档，请求用户明确接受

```
## 风险与歧义确认

### 已知歧义
- [歧义 1]：[具体内容] — 潜在影响：[说明]
- [歧义 2]：[具体内容] — 潜在影响：[说明]

### TBD 项目
- TBD-X: [具体内容]
- TBD-Y: [具体内容]

### 潜在影响
- [如果在 TBD 未解决的情况下实施，可能出现的后果]

### 确认
你是否接受上述风险，在 TBD 未完全解决的情况下开始实施？

💡 如果你有其他相关信息想补充，欢迎直接说明。
```

4. **用户确认后**：开始实施，并在实施过程中保持 TBD 和风险可见
5. **实施过程中发现 TBD 的答案时**：更新 Spec+RFC，继续推进
