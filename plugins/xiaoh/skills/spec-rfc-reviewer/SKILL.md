# Spec+RFC 准入检查

对当前完整修订执行一次证据化检查。只检查源工件，不生成 OpenSpec、不修改代码、不启动 Agent，也不自动触发修订后的下一轮检查。

## 输入

至少取得完整 Spec+RFC 或等价需求设计工件。按需读取项目规则、术语、当前架构、接口和约束。缺少决定性材料时明确标为未验证，不凭记忆补齐。

## 检查流程

1. 确认工件身份、路径、修订号和适用范围。
2. 提取目标、非目标、FR、NFR、接口、数据、权限、安全、兼容、迁移、失败行为、测试、回滚、风险和 TBD。
3. 检查目标与需求、需求与设计、设计与验收是否可追溯。
4. 检查矛盾、无来源固定值、隐含范围扩大、职责错位、生命周期遗漏和不可验证表述。
5. 对每个问题给出精确位置、证据、影响和最小修正建议。
6. 给出一次性结论。修订后仅在用户再次要求或上层流程明确调用时重新执行。

## 判断维度

- 产品：目标、用户价值、范围、优先级和成功标准是否明确。
- 领域：术语、状态、不变量、归属和生命周期是否一致。
- 工程：模块、数据、接口、错误、并发、幂等、恢复和运维是否可实施。
- 安全：权限、信任边界、敏感数据、降级和审计是否充分。
- 兼容：旧行为、迁移、回退和跨版本边界是否明确。
- 验证：每项必须行为是否有可观察的验收条件和测试策略。

## 输出

```markdown
## 结论

结论：OPENSPEC_READY / OPENSPEC_READY_WITH_FIXES / OPENSPEC_NOT_READY
审核对象：<路径或标识>，修订 <revision>
一句话判断：...

## 阻塞项
- [P0] 位置、证据、影响、修正建议

## 主要问题
- [P1] ...

## 次要建议
- [P2] ...

## 准入覆盖
| 维度 | 状态 | 证据或缺口 |
|---|---|---|

## 未验证范围与风险
- ...
```

## 结论规则

- `OPENSPEC_READY`：无阻塞项，关键语义完整且可验证，可基于当前修订生成 OpenSpec。
- `OPENSPEC_READY_WITH_FIXES`：没有会改变核心业务结果的阻塞，但存在应在派生前修正的明确缺口。
- `OPENSPEC_NOT_READY`：存在关键需求遗漏、矛盾、设计不可实现、安全/迁移边界缺失或无法形成可验证验收条件。

不要用评分掩盖阻塞项，不把代码现状当作目标需求，不把个人偏好写成必须修改。
